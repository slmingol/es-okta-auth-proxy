es-okta-auth-proxy

An authentication proxy that gates Elasticsearch access behind Okta SSO -- translating OIDC identity into ES API key credentials without requiring a paid Elastic license.

Node 18+ ECK / Basic License Okta OIDC ES API Keys Docker

Why this exists

Elasticsearch's native SSO support (SAML, OIDC, LDAP) requires a Gold or Platinum license. Clusters provisioned by the ECK operator on a basic/free license have no way to front-end ES with Okta authentication out of the box.

This proxy fills that gap. It sits between clients and Elasticsearch, enforces Okta login, and injects a pre-issued ES API key on every proxied request. From Elasticsearch's perspective, every request arrives authenticated -- it never touches the user's identity directly.

Analogy to the existing Kibana pattern. Your current logs/metrics stack has all users land in Kibana via a single ipausers LDAP group -- Kibana holds its own service-account key and ES never sees individual users. This proxy is the same architecture for direct ES access: one Okta-gated entry point, one (or a few) API keys carrying the permissions.

How it works

The proxy is a Node/Express app that combines an OIDC client (openid-client) with http-proxy-middleware. Two things happen on every request: authentication is checked, and if valid, the Authorization header is replaced with a pre-issued ES API key before the request is forwarded.

Request lifecycle

1
Unauthenticated request hits proxy. requireAuth middleware checks req.session.user. If absent, stores the original URL in session.returnTo and redirects to /auth/login.
2
Okta OIDC login. Proxy generates state + nonce, redirects to Okta authorization URL with scopes openid email profile groups.
3
Callback. Okta posts tokens to /auth/callback. Proxy validates state/nonce, extracts claims -- sub, email, name, groups[] -- and writes them to the session.
4
API key resolution. On every proxied request, resolveApiKey(groups) picks the correct ES API key. With no group map loaded, it falls back to ES_API_KEY -- a single key used for all authenticated users.
5
Header swap. The proxy strips any incoming Authorization header and sets Authorization: ApiKey <key> plus X-Forwarded-User and X-Forwarded-Groups for downstream observability.
6
Response passes through. ES processes the request under the API key's permissions and returns results directly to the client.

Current configuration: single-key mode

The simplest deployment mirrors the ipausers Kibana pattern: every authenticated Okta user shares one ES API key. No group mapping file is needed.

Optional: group-based key mapping

When different Okta groups need different ES access levels, a JSON config file maps group names to separate API keys. If the file doesn't exist, the proxy silently falls back to ES_API_KEY -- no restart required to add mapping later.

config/group-map.json

{
  // Priority order -- first matching group wins
  "_priority": ["es-admin", "es-write", "es-readonly"],

  "es-admin":    "BASE64_KEY_WITH_SUPERUSER_PERMS",
  "es-write":    "BASE64_KEY_WITH_WRITE_PERMS",
  "es-readonly": "BASE64_KEY_WITH_READ_PERMS",

  // Fallback when no group matches
  "_default": "BASE64_KEY_FALLBACK"
}

The _priority array controls tie-breaking for users in multiple groups. A user in both es-admin and es-readonly gets the es-admin key because it appears first.

Mount as a Kubernetes ConfigMap. In production, don't commit the real group-map.json. Create a K8s ConfigMap (or use Vault via VSO), mount it at /config/group-map.json, and set GROUP_MAP_PATH=/config/group-map.json. The docker-compose mounts ./config read-only for local dev; the same pattern works for K8s volumes.

Resolution logic (src/group-map.js)

// No map loaded -- single-key mode
if (!groupMap) return process.env.ES_API_KEY;

// Walk priority list, return first matching group's key
for (const g of priority) {
  if (groups.includes(g) && groupMap[g]) return groupMap[g];
}

// _default in map -- ES_API_KEY env var
return groupMap._default ?? process.env.ES_API_KEY;

What Elasticsearch sees

On basic license, ES has no awareness of the user's Okta identity. It only sees the API key. The proxy forwards two informational headers that downstream systems or custom ES plugins can log, but ES itself does not enforce them.

X-Forwarded-User

The authenticated user's Okta email. Present on every proxied request when a session exists.

X-Forwarded-Groups

Comma-separated list of Okta groups from the ID token claims. Useful for audit log parsing.

No per-user audit trail in ES. All members of a group are indistinguishable at the Elasticsearch layer -- they share one API key. Application-level audit trails require reading the proxy's own logs or adding a logging middleware layer. Per-user ES audit logging requires Gold+.

Token and session lifecycle

Okta tokens

On successful login the proxy receives two tokens from Okta, both stored in the Express session:

TokenStored asUsed forLifetime
ID token (JWT)session.idTokenid_token_hint on Okta end-session redirectTypically 1 hour (Okta default)
Access tokensession.accessTokenRevocation via /auth/revokeTypically 1 hour (Okta default)

The proxy does not use a refresh token and does not silently re-authenticate. When the Express session expires the user is simply redirected to Okta for a fresh login. The session lifetime is controlled by the express-session cookie settings (in-memory store by default -- sessions are lost on pod restart).

User identity claims (email, name, groups[]) are extracted from the ID token at login and stored in session.user. Group membership is resolved once at login -- mid-session Okta group changes do not take effect until the next login.

Logout mechanics

/auth/logout
Calls req.session.destroy(). Clears the local Express session cookie. The Okta SSO session remains active -- the user can log back in with no prompt if Okta's session is still valid. Use this for "soft" logout.
/auth/revoke
Calls oidcClient.revoke(accessToken, 'access_token') to invalidate the access token on Okta's side, destroys the local session, then redirects to Okta's /oauth2/default/v1/logout endpoint with id_token_hint. This terminates the Okta SSO session globally -- the user is fully signed out of all apps sharing the Okta session.

ES API key rotation

Separate from Okta tokens, the proxy can rotate its own ES API keys on a schedule. This is configured via KEY_ROTATION_HOURS and requires ES_ROTATION_CREDS (Basic auth, recommended) or ES_ROTATION_KEY (API key with manage_api_key privilege).

Rotation sequence per group:

1
Creates a new ES API key via POST /_security/api_key with the role descriptors from _roles in group-map.json.
2
Writes the new key to the group-map file and swaps it into memory atomically -- requests never gap between old and new key.
3
Invalidates the old key via DELETE /_security/api_key. This step is non-fatal -- if it fails, the old key expires naturally or can be cleaned up manually.
Basic auth over API key for rotation. ES derived keys cannot create or invalidate other API keys -- only keys with manage_api_key granted at the user level can. Using ES_ROTATION_CREDS=elastic:password (Basic auth) sidesteps this restriction.

Expanding RBAC: next steps

The architecture supports a graduated rollout. Start with single-key mode; add tiers only when a concrete requirement surfaces.

01
Define ES roles with role_descriptors For each access tier you need, create a separate ES API key scoped to the right indices and privileges. Document the role boundary: which indices, which operations (read / write / manage), and whether field-level security (FLS) or document-level security (DLS) is needed -- both available on basic license.
02
Mirror groups in Okta Create Okta groups that match the tier names (e.g. es-admin, es-metrics-write, es-readonly). Assign users. The proxy's OIDC scope already requests the groups claim -- no code changes needed, only Okta configuration.
03
Populate group-map.json Add an entry per group pointing to the base64-encoded API key. Set _priority to the order that breaks ties -- most privileged first. Store the file as a Kubernetes Secret or in Vault, mounted at GROUP_MAP_PATH.
04
Automate key rotation ES API keys support an expiration field. Set a rotation schedule (e.g. 90 days), script the key re-creation via the ES API, and update the K8s Secret. A rolling reload -- SIGHUP or container restart -- picks up the new map without downtime.
05
Add proxy-layer audit logging Since ES can't audit by user on basic license, add request logging middleware in the proxy: timestamp, X-Forwarded-User, method, path, response status. Ship to your existing log aggregation stack. This reconstructs per-user access history without an ES license upgrade.
06
Upgrade path: native OIDC (Gold+) If a license upgrade becomes available, ES native OIDC eliminates the proxy entirely -- users authenticate directly and ES enforces role mappings from the token. The Okta group structure you build now maps directly to ES role mappings, so the operational model carries forward.
